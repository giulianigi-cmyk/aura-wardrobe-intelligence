## 2. Architettura account

| Tipo | role | subscription_plan | Override | Come si ottiene |
|---|---|---|---|---|
| Il tuo account | `owner` | `free` | **sì**, server-side | SQL una tantum (service role) |
| Utente reale | `user` | `free` | no | default per ogni nuovo account (nessuna riga = free) |
| Test PLUS | `user` | `plus` (`source = 'manual'`) | no | SQL una tantum |
| Test ULTRA | `user` | `ultra` (`source = 'manual'`) | no | SQL una tantum |

Regole:
1. **Ruolo e piano in due tabelle distinte**, mai su `profiles`: la policy RLS attuale `Users can update own profile`
   permette all'utente di modificare ogni colonna del proprio profilo dal browser.
2. Nessuna policy di scrittura per `authenticated` su ruolo/piano/contatori: scrive solo il server (service role).
3. **Owner override**: il server legge `user_roles.role` dal DB a ogni controllo. `owner` ⇒ feature tutte attive e quote
   non bloccanti (l'uso viene comunque registrato, utile per stimare i costi).
4. **Simulazione piano per l'owner** (per testare paywall e limiti senza cambiare account): colonna
   `user_roles.simulated_plan` (`null` | `free` | `plus` | `ultra`), modificabile **solo** da una server function che
   verifica `role = 'owner'` nel DB. Con `simulated_plan` impostato l'owner si comporta esattamente come quel piano
   (override disattivato); con `null` torna override completo. Il piano reale resta `free`.
5. Nessun uso di localStorage, query param o flag JS per ruolo/piano: il client riceve lo stato dal server solo per
   mostrare la UI.

## 3. Architettura entitlement

### 3.1 Cosa sta nel database e cosa in configurazione

| Dato | Dove | Perché |
|---|---|---|
| Ruolo dell'utente, simulazione owner | **DB** `user_roles` | stato per utente, deve essere a prova di manomissione |
| Piano corrente, stato, scadenza, origine | **DB** `user_subscriptions` | stato per utente, in futuro aggiornato dagli store |
| Consumo quote nel periodo | **DB** `usage_counters` | deve essere atomico e condiviso tra richieste |
| Storico eventi di acquisto/rinnovo | **DB** `subscription_events` — **rimandato** alla fase store | serve solo quando arrivano i webhook Apple/Google |
| Elenco feature, piano minimo, tipo di quota, limiti per piano, periodo | **Config** `src/lib/plans/catalog.ts` | uguale per tutti, versionato in git, tipizzato, condiviso server/client, nessuna query |
| Testi del paywall | **Config** i18n (`it/en/es/fr.json`) | già gestiti così |
| Product ID degli store | **Config** catalogo (fase store) | statici per piano |
| Prezzi | **Store** (non nel codice) | li fornisce App Store / Play |

Cambiare un numero o spostare una feature da PLUS a ULTRA = modificare una riga del catalogo + deploy.
(Una tabella `plan_limits` nel DB permetterebbe modifiche senza deploy, ma oggi non serve: deploy Lovable è rapido.)

### 3.2 Tabelle (proposta minima: 3 subito, 1 in fase store)

```sql
-- 1. Ruolo (separato dal piano)
user_roles (
  user_id        uuid primary key references auth.users on delete cascade,
  role           text not null default 'user' check (role in ('user','owner')),
  simulated_plan text null check (simulated_plan in ('free','plus','ultra')),
  updated_at     timestamptz not null default now()
)
-- RLS: SELECT solo della propria riga. Nessuna INSERT/UPDATE/DELETE per authenticated.

-- 2. Piano (una riga per utente = stato corrente; nessuna riga = free)
user_subscriptions (
  user_id                 uuid primary key references auth.users on delete cascade,
  plan                    text not null check (plan in ('free','plus','ultra')),
  status                  text not null check (status in ('active','trialing','grace','expired','canceled')),
  source                  text not null check (source in ('manual','app_store','play_store')),
  current_period_end      timestamptz null,     -- null = senza scadenza (manual)
  product_id              text null,            -- fase store
  original_transaction_id text null,            -- fase store (restore / dedup)
  environment             text null check (environment in ('production','sandbox')),
  updated_at              timestamptz not null default now()
)
-- RLS: SELECT solo della propria riga. Scrive solo il server.

-- 3. Contatori (solo per le quote "a consumo"; le quote "per numero di elementi" si contano sulle tabelle esistenti)
usage_counters (
  user_id     uuid references auth.users on delete cascade,
  feature     text not null,     -- chiave del catalogo, es. 'stylist_message'
  period_key  text not null,     -- '2026-10' (mensile), '2026-10-01' (giornaliera), 'lifetime' (una tantum)
  count       integer not null default 0,
  primary key (user_id, feature, period_key)
)
-- RLS: SELECT solo propria riga (per mostrare "ti restano N").
-- Scrittura SOLO tramite funzione SECURITY DEFINER consume_quota(user, feature, period_key, limit, units)
-- con EXECUTE revocato ad anon/authenticated e concesso solo a service_role.
-- Il limite lo calcola il server dal catalogo: il client non lo passa mai.

-- 4. (fase store) subscription_events: log append-only dei webhook (purchase, renew, expire, cancel, refund, restore)
```

Piano effettivo = `user_subscriptions.plan` se `status in ('active','trialing','grace')` e
(`current_period_end` nullo o futuro), altrimenti `free`.

### 3.3 Controlli

```text
Server function AI ──► enforceFeature(ctx, 'stylist_message')
                         │ 1 query: user_roles + user_subscriptions (service role, per userId del JWT)
                         │ owner senza simulazione ─► consentito (uso registrato, nessun blocco)
                         │ piano effettivo < piano minimo ─► errore { code:'upgrade_required', feature, requiredPlan }
                         │ quota a consumo ─► consume_quota() atomico (insert … on conflict … where count+units <= limit)
                         │     superata ─► errore { code:'quota_exceeded', feature, limit, resetsAt, upgradePlan }
                         │ quota per elementi ─► count(*) sulla tabella (wardrobe_items, trips, wardrobe_locations…)
                         ▼
                       chiamata AI ── se fallisce ─► refund_quota() (non si paga un errore)
```

- Una riga `await enforceFeature(context, '<feature>')` nelle server function che costano (≈ 20) e nelle insert soggette
  a limite di elementi. Non sono "controlli sparsi": la regola sta nel catalogo, la chiamata indica solo quale feature è.
- Le insert fatte **direttamente dal client** su Supabase (es. `wardrobe_items` da `AddItem.tsx`, `trips`) non passano
  da server function: per i limiti "per numero di elementi" serve un controllo anche lato DB (trigger `BEFORE INSERT`
  che legge piano + limite) oppure spostare quelle insert in server function. Da decidere in implementazione;
  il trigger è la modifica più piccola e non tocca i componenti.
- **Client** (solo UX, mai sicurezza): `getMyEntitlements` (server fn) → `useEntitlements()` in React Query →
  `<PaywallSheet>` unico che mostra "Disponibile con PLUS" o "Disponibile con ULTRA" in base a `requiredPlan` e al piano
  corrente; gli errori `upgrade_required` / `quota_exceeded` delle server function aprono lo stesso sheet.

## 5. Wrapper mobile: A vs B

Fatti verificati sul progetto (rilevanti per entrambe):
- L'app vive su una sola route `/` con navigazione a stato interno (`AuraApp.tsx`); **nessun loader SSR** sulla route
  principale → la UI può girare come SPA. Usano loader solo `/.lovable/oauth/consent` (MCP, solo web).
- Le server function sono chiamate a **URL relativi** `/_serverFn/<id>`; il token Supabase viaggia in header
  `Authorization: Bearer` (`auth-attacher.ts`), **non in cookie**.
- La versione installata di TanStack Start (1.168.60) supporta `createStart({ serverFns: { fetch } })` (fetch globale
  personalizzabile) e la **SPA mode** (`tanstackStart({ spa: { enabled: true } })`).
- Gli ID delle server function sono `sha256(file + nome export)` (`start-plugin-core/.../compiler.js:302`): **stabili
  tra build** finché file e nome non cambiano.
- URL web hardcoded: `use-auth.tsx` (`APP_URL` per conferma email e reset password), `aura-share.ts`,
  `google-calendar.server.ts`, `outlook-calendar.server.ts`, callback in `routes/api/public/hooks/*-callback.ts`.
- Il login OAuth del **calendario Google** è aperto nella pagina: Google **blocca l'OAuth nelle WebView incorporate**
  (`disallowed_useragent`), quindi in entrambe le opzioni va aperto nel browser di sistema e si torna con un deep link.
- Fotocamera e galleria via `<input type="file" capture>` (AddItem, OutfitScan, Shop, selfie armocromia); microfono via
  `getUserMedia` + `MediaRecorder` (StylistChat); posizione via `navigator.geolocation` (`use-location.tsx`).

| Aspetto | **A. Capacitor + `server.url` → sito remoto** | **B. Capacitor + client bundled + server function remote** |
|---|---|---|
| Modifiche al progetto | Aggiungere Capacitor (config + progetti `ios/` `android/`), deep link, OAuth calendario nel browser di sistema, permessi nativi. Il codice web resta quasi identico. | Tutto quanto in A **più**: build SPA separata per mobile; `serverFns.fetch` che antepone l'origin del server (`VITE_API_ORIGIN`); CORS su `/_serverFn/*` per le origin `capacitor://localhost` (iOS) e `https://localhost` (Android); routing dei deep link dentro la SPA; storage sessione Supabase adatto all'app. La build web SSR su Cloudflare resta invariata. |
| File coinvolti | nuovi: `capacitor.config.ts`, `ios/`, `android/`, file di associazione in `src/routes/[.well-known]/`; modificati: `package.json`, `use-auth.tsx`, `CalendarConnectionSection.tsx`, `google-/outlook-calendar.server.ts`, `*-calendar-callback.ts`, `aura-share.ts` | quelli di A + `vite.config.ts` (target mobile/SPA), `src/start.ts` (fetch globale + middleware CORS), eventualmente `src/server.ts` (preflight `OPTIONS`), `integrations/supabase/client.ts` (storage sessione — file generato da Lovable, da gestire con cautela), `AuraApp.tsx` (deep link → schermata) |
| Vantaggi | Rapidissima da realizzare; ogni deploy web aggiorna subito l'app; nessuna CORS; una sola build | UI e JS caricati dal dispositivo: avvio veloce e indipendente dalla rete; esperienza più "app"; minor rischio di rifiuto Apple; base solida per funzioni native |
| Svantaggi | Ogni avvio scarica l'app dalla rete (oggi ≈ 630 KB gzip di JS); niente funzionamento senza rete; la documentazione Capacitor indica `server.url` per il live-reload in sviluppo, non per la produzione | Più lavoro iniziale; doppio target di build; le modifiche UI richiedono un rilascio store (o un servizio di live update); **compatibilità di versione**: un'app installata vecchia chiama server function nuovi — rinominare/spostare una server function rompe le versioni installate |
| Performance | Dipende dalla rete a ogni cold start; lo splash SSR + JS remoto peggiorano il TTI | Shell istantanea da disco; restano solo le chiamate API; il lazy-loading resta utile (parse time) |
| Review Apple | **Rischio alto** (Guideline 4.2 *minimum functionality*: app che sono essenzialmente un sito web) e possibili obiezioni a cambi di comportamento senza review | Rischio moderato: UI locale + funzioni native (camera, push, acquisti in-app) la rendono un'app vera |
| Review Google | Più tollerante con le WebView, ma servono comunque Play Billing per gli abbonamenti, modulo Data safety e **link web per la cancellazione account** | Uguale ad A per i requisiti di policy; nessun rischio specifico in più |
| Fotocamera / foto | `<input capture>` funziona in WKWebView e nella WebView Android di Capacitor; servono le stringhe di permesso (`NSCameraUsageDescription`, `NSPhotoLibraryUsageDescription`) | Uguale; opzionale `@capacitor/camera` per UX migliore |
| Microfono | `getUserMedia` funziona in WKWebView (iOS recenti) e su Android con permesso `RECORD_AUDIO` gestito da Capacitor; serve `NSMicrophoneUsageDescription` | Uguale (origin `capacitor://localhost` è secure context) |
| Posizione | `navigator.geolocation` + `NSLocationWhenInUseUsageDescription` / permesso coarse | Uguale |
| Deep link | Universal Links / App Links che aprono direttamente il path nella WebView remota: semplice | Universal/App Links + listener `appUrlOpen` che porta alla schermata giusta nella SPA |
| Autenticazione | Sessione Supabase in localStorage dell'origin remoto: funziona com'è. Conferma email/reset: `APP_URL` → link universale. | Sessione in localStorage di `capacitor://localhost` (o storage nativo); stessi redirect via link universale; il token resta in header, quindi nessun problema cookie |
| API | Stessa origin, nulla da cambiare | Server function verso origin assoluta via `serverFns.fetch`; le chiamate dirette a Supabase e alle API pubbliche (open-meteo, ecc.) restano invariate |
| CORS | Non serve | Serve solo su `/_serverFn/*` (e sulle route API chiamate dal client), con allowlist delle origin dell'app; niente `credentials` perché si usa il Bearer token |
| Manutenzione | Minima, ma il rischio review resta a ogni aggiornamento | Regola fissa: non rinominare/spostare server function senza lasciare l'alias; endpoint "versione minima supportata" per forzare l'aggiornamento; pipeline di build mobile (Xcode / Android Studio o CI) fuori da Lovable |

**Raccomandazione: B.**
Motivi tecnici: (1) la causa principale di rifiuto Apple per un'app come AURA è la 4.2, e A ne è l'esempio tipico;
(2) l'architettura attuale è già quasi pronta per B — route unica senza loader SSR, auth via Bearer (niente cookie
cross-origin), `serverFns.fetch` e SPA mode supportati dalla versione installata, ID server function deterministici;
(3) con il client sul dispositivo il costo del bundle iniziale smette di dipendere dalla rete, che oggi è il problema
di performance maggiore; (4) i lavori comuni ad A e B (deep link, OAuth calendario nel browser di sistema, permessi,
acquisti in-app) vanno fatti comunque. A ha senso solo come prototipo interno su TestFlight / test interno Play,
non come build da sottomettere.

## 7. Cancellazione account — analisi

Funzione attuale: `src/lib/delete-account.functions.ts` → svuota `avatars`, `outfits`, `wardrobe` (fino a 2 livelli,
`list(..., { limit: 1000 })`), poi `auth.admin.deleteUser()`; il commento dice che "ogni FK verso auth.users è ON DELETE CASCADE".

### 7.1 Bucket non svuotati

| Bucket | Contenuto | Path | Policy (live) | Riferimenti DB | Stato oggi |
|---|---|---|---|---|---|
| `avatar-private` | foto avatar per try-on (viso + corpo) e immagini risultato del try-on | `{uid}/photo-*`, `{uid}/tryon-*` | SELECT/INSERT/UPDATE/DELETE solo cartella propria (authenticated) | `user_avatar.photo_path`, `user_avatar.avatar_image_path`, `avatar_tryon_cache.result_image_path` (righe in cascade) | 11 file, 68,8 MB |
| `outfit-photos` | foto degli outfit indossati (scansione / log wear) | `{uid}/wear-*.jpg` | SELECT/INSERT/DELETE cartella propria (ruolo `public` ma con `auth.uid()`) | `outfit_photo_detections.photo_path` (cascade) | 18 file, 46,4 MB |
| `shared-library` | copie **anonimizzate** delle immagini dei capi condivisi in libreria | `{uuid-random}.ext` (nessun uid nel path) | SELECT per qualsiasi utente autenticato; scrive solo il server | `shared_library_items.image_url / thumbnail_path / source_image_path`, legate all'utente solo tramite `owner_hash` (HMAC) | 36 file, 3 senza riga (già orfani) |

### 7.2 Altri problemi trovati (più gravi)

| Problema | Evidenza | Effetto |
|---|---|---|
| **`profiles` non ha FK verso `auth.users`** | nessun vincolo su `profiles.id` | dopo la cancellazione restano nome, data di nascita, città, coordinate, username, preferenze. **3 profili orfani già presenti** in produzione |
| `outfit_plans` e `wardrobe_item_valuations` senza FK su `user_id` | verificato su `pg_constraint` | righe orfane dopo la cancellazione |
| Tabelle chat legate a `profiles` (non ad `auth.users`) | `messages.sender_id`, `conversations.created_by`, `message_comments.user_id` → `profiles` con **NO ACTION**; `conversation_participants`, `message_reactions`, `user_blocks` → `profiles` CASCADE | aggiungere la cascade su `profiles` farebbe **fallire** la cancellazione per chi ha scritto messaggi, se non si decide prima cosa fare dei messaggi (cancellarli o anonimizzarli) |
| `shared_library_items` non viene cancellata | il trigger `purge_shared_library_on_revoke` scatta solo su UPDATE del consenso, non sulla cancellazione | le copie anonimizzate dei capi restano nella libreria condivisa |
| Svuotamento storage senza paginazione | `list(prefix, { limit: 1000 })` | una cartella con più di 1000 file viene svuotata solo in parte: la cartella `wardrobe` più grande oggi ha **1126 file** |
| `products.created_by` → SET NULL | vincolo `n` | i prodotti importati restano (catalogo condiviso): accettabile, da dichiarare |

Osservazione collaterale (non legata alla cancellazione): nel bucket `wardrobe` 914 file su 1892 (≈ 433 MB) non sono
referenziati da `wardrobe_items` o `scan_jobs` — probabilmente originali pre-scontorno o capi eliminati. Da verificare
prima di qualsiasi pulizia.

### 7.3 Piano di correzione (da approvare, non applicato)

1. Storage: aggiungere `avatar-private` e `outfit-photos`; paginare `list()` fino a esaurimento; profondità dinamica.
2. `shared-library`: prima di cancellare l'utente, cancellare le righe con `owner_hash = shared_library_owner_hash(uid)`
   e rimuovere i relativi file.
3. Chat: decidere la politica (consiglio: **anonimizzare** i messaggi inviati, cioè sender → profilo "utente eliminato",
   per non rompere le conversazioni degli altri; in alternativa cancellarli).
4. DB: aggiungere FK `profiles.id → auth.users ON DELETE CASCADE`, `outfit_plans.user_id` e
   `wardrobe_item_valuations.user_id` con CASCADE (dopo aver ripulito gli orfani esistenti).
5. Ordine dell'operazione: shared library → chat → storage (paginato) → `deleteUser` (cascade su tutto il resto).
6. Per Google Play: pagina web pubblica per richiedere la cancellazione (requisito Play).
7. Test: account di prova con dati in tutte le tabelle/bucket → cancellazione → query di verifica zero residui.
